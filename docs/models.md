# Models: conventions and pipeline

Everything in `public/models` and `public/chunks` is generated by `tools/gen` (procedural
recipes, no DCC tool needed). Hand-made GLBs from Blender follow the same rules.
Textures and the material library are documented in `docs/materials.md`.

## Commands

```bash
npm run gen            # models + chunks (also runs automatically before dev/build when missing)
npm run gen:models     # tools/gen/assets/*.mjs -> public/models/<id>.glb (+ <id>.json, index.json)
npm run gen:chunks     # tools/gen/city.mjs -> public/chunks/<x>_<z>.glb (+ .json sidecar)
node tools/gen/index.mjs models --only prop_bollard_a --no-pack
npm run dev            # then open /viewer.html
```

Viewer (`/viewer.html`): `?cat=prop|building|sign|vehicle|character`, `?id=a,b`, `?view=chunk&chunk=0_0&radius=1`,
`&light=day|night` (night = cyber environment + bloom, day = bright inspection light), `&tex=0` (GLB fallback
factors only, no texture library), `&tier=high|medium|low`, `&wire=1`, `&uvtest=1` (puts an upright "F" checker
on every tiled material), `&anim=walk` (characters), `&row=<metres>` (gallery row width),
`&cam=alphaDeg,betaDeg,radius[,tx,ty,tz]`. The viewer binds the shared material library exactly like the game.

`CITY_TALLY=1 node tools/gen/index.mjs chunks` prints, per chunk, where the triangles go (roads, buildings,
furniture, alleys, plazas, parking lots).

## Space and units

- Metres. +Y up, +X east, +Z north. This is Babylon's left-handed world.
- Recipes are authored in that space. The exporter converts to glTF (x is negated and
  winding reversed, because Babylon mirrors X when it imports glTF), so a GLB loaded in
  Babylon reproduces the authored geometry exactly. Blender users: export with the default
  glTF settings and mirror in your head the same way, or just use the recipes.
- Model origin: ground level, centre of the footprint. The "front" (shop door, sign side) faces +Z.
- Headings (`rotY`) are compass angles: 0 = north (+Z), pi/2 = east (+X).
- Chunk GLB `<x>_<z>.glb` covers x in [0,128], z in [0,128] chunk-local (game space);
  `ChunkManager` puts its root at (x*128, 0, z*128). Road grid: corridors are centred on
  chunk-local 0, 64 and 128 on both axes (see `tools/gen/lib/modules.mjs`).

## Modules (so facade textures tile without cutting windows)

| thing | size |
| --- | --- |
| floor height | 3.6 m |
| ground-floor shopfront | 4.8 m |
| window bay | 3.0 m |
| facade tile | 4 bays x 2 floors = 12 x 7.2 m (shopfront 12 x 4.8) |
| road asphalt | 14 m (4 x 3.5 m lanes); sidewalk 3 m each side; curb 0.15 m |
| road corridor | 20 m; grid pitch 64 m; block interior 44 m |
| lots | 21 x 21 (four per block), 21 x 42 (two), 42 x 42 (one), 2 m alleys |

Building width and depth are multiples of 3 m, height is `4.8 + (floors-1) * 3.6`.
Facade walls start at a bay boundary (u is a multiple of 3 from the corner), so tile seams never fall inside a window.
The facade textures have floor lines at tile boundaries (windows 1.8 x 2.0 m, sill 0.95 m above the floor).
With `v = -y`, floors line up when the ground floor is 3.6 m. Above a 4.8 m shopfront pass `vOff: -4.8`
to `wall`/`box`/`prism` so floor lines land on 4.8 + 3.6k.

## Materials

- `material.name` is always an ID from `tools/gen/lib/materials.mjs` (`mat_<category>_<name>`).
  The generator throws on unknown IDs. Add new ones there and tell the texture work.
- GLBs contain no textures. The runtime material library swaps in the shared textured
  material by name, so every chunk uses the same texture memory.
- GLB materials carry fallback factors (base colour, metallic, roughness, emissive,
  `KHR_materials_emissive_strength` for neon) so models look right before textures exist.
  `material.extras` carries `{ tile, atlas, tint }` hints.
- Neon and lights are pure emissive materials (`mat_neon_*`, `mat_light_warm`, `mat_veh_light_*`).
  Bloom is a runtime post effect; do not fake glow with extra geometry.
- `mat_veh_paint`, `mat_char_skin`, `mat_char_cloth`, `mat_fabric_awning`, `mat_metal_container` have `tint: true`: their
  base colour is light and the colour of the individual model comes from `COLOR_0`. The runtime material
  **must** keep vertex colours enabled on these (the library does).
- `mat_atlas_decal` is alpha-blended (road arrows, manholes, stains, drain grates) and sits 4.5 cm above the
  road; it needs `zOffset` / depth bias at runtime to avoid z-fighting at distance.
- Every material id in `tools/gen/lib/materials.mjs` has an entry in the texture manifest (53 in total). A new id needs a
  matching texture recipe (`tools/textures`, `required-ids.json`); until then the GLB fallback factors are used and
  the library logs one warning per id.

## Vertex data

- `POSITION`, `NORMAL`, `TEXCOORD_0`, `COLOR_0`. No `TANGENT` (the runtime derives it), no `TEXCOORD_1` yet.
- `COLOR_0.rgb` multiplies base colour: baked ambient occlusion (darker near the ground
  and in corners) and tint. The material library must enable vertex colours on these materials.
- `-vtf`: UVs stay float32 in the packed GLB. Positions are 14-bit quantised, normals 8-bit.

## UV0

- Tiling surfaces: **metres**, 1.0 = 1 m. The material library scales by the material's `tileSizeM`.
  u grows to the right of a viewer who looks at the face from outside, v grows **downward**
  (glTF image space, v = 0 is the top row), so on walls `v = -y` and floors line up with tile boundaries.
  Horizontal faces: `u = x`, `v = -z` (north is image-up). Verified with `viewer.html?uvtest=1`.
- Atlas materials (`mat_atlas_signs`, `mat_atlas_billboard`): UV0 is the 0-1 atlas coordinate,
  written at generation time into the sprite rect (gltfpack merges meshes per material, so the
  runtime cannot remap later). Rects come from `public/textures/atlas/<atlas>.json`, which the
  texture work owns; `tools/gen/lib/atlas.mjs` reads them verbatim (see `docs/atlas.md`).

## Budgets (triangles, LOD0)

| kind | budget |
| --- | --- |
| small prop (bollard, bin, hydrant) | 200 |
| medium prop (lamp, bench, vending, traffic light) | 500 |
| big prop (bus stop, kiosk, billboard) | 900 |
| sign piece | 400 |
| low-rise / mid-rise building | 1500 |
| tower | 3500 |
| vehicle | 3000 |
| character | 2500 |
| chunk | 60 000 |

`npm run gen:models` fails when a recipe exceeds its budget. Generated vertices are not shared
between flat faces (hard edges), so a quad costs 4 vertices; the monitor's geometry estimate
assumes about 24 bytes per vertex after packing.

## City layout (`tools/gen/city.mjs`)

- The world is an endless grid of 128 m chunks (`public/chunks/<cx>_<cz>.glb`, radius 2 around the origin is
  generated: 25 chunks, about 13 MB on disk). Roads are 14 m wide with 3 m sidewalks, centred on chunk-local
  x or z = 0 / 64 / 128; a block (44 m + sidewalks) sits between them, so 4 blocks per chunk.
- Every block is split into 1, 2 or 4 lots (21 m or 42 m wide, 2 m alleys). A lot gets a building, now and then a
  plaza (props only) or a parking lot (asphalt + parked cars). The building comes from the recipes tagged
  `zone:downtown|mid|commercial|residential|industrial`, chosen by distance from the world origin; the lot
  decides footprint (snapped to the 3 m bay) and facing.
- Street furniture on the sidewalks: street lights every ~32 m, small props, barriers, traffic lights on the
  four block corners, parked cars in the kerb lane (right-hand traffic).
- Chunk geometry is flattened into one mesh per material (`flatten: true`) and packed with gltfpack.
- Everything is seeded (`hash(cx, cz, ...)`), so a chunk is identical on every machine and every run.
- Budget: a chunk stays below 60 000 triangles. Parked cars are the heaviest items (about 1500 each), so they
  stop being placed once a chunk reaches `SOFT_CHUNK_TRIS` (44 000). Today the 25 chunks have 28k - 46k
  triangles (955k in total), so the radius-1 neighbourhood the game keeps loaded is about 350k - 400k.

### Chunk sidecar `<cx>_<cz>.json`

```jsonc
{
  "chunk": [0, 0], "size": 128, "tris": 45378,
  "anchors":   [{ "name": "light.entrance", "pos": [x, y, z], "rotY": 0, "color": "#ffd9a0", "intensity": 1, "range": 14 }],
  "colliders": [{ "c": [x, y, z], "h": [hx, hy, hz], "rotY": 0 }],   // oriented boxes, chunk-local metres
  "lots":      [{ "cx": 32, "cz": 32, "kind": "building", "id": "bhigh_...", "floors": 28, "heading": 0, "w": 36, "d": 36 }],
  "roads":     { "width": 14, "sidewalk": 3, "laneOffsets": [-5.25, -1.75, 1.75, 5.25],
                 "alongX": [{ "z": 0, "x0": 0, "x1": 128 }, ...], "alongZ": [{ "x": 0, "z0": 0, "z1": 128 }, ...] },
  "spawns":    [{ "type": "player", "pos": [72.5, 0.15, 36], "rotY": 0 }]   // only on chunk 0_0
}
```

`anchors` named `light.*` are meant for the runtime light pool (a handful of real point lights near the player;
everything else is emissive material plus bloom). `roads` gives traffic and navigation the lane centre lines.

## Gameplay data

- `b.anchor(name, pos, extras)`: marker. In prop GLBs it is a node `anchor_<name>`; in chunks it goes
  to the sidecar JSON (`anchors`). Used for point lights (`light.*`), spawns, parking spots, doors.
- `b.collider({ c, h })`: oriented box in the sidecar `colliders` (centre, half extents, `rotY`) for Rapier.
- `b.node(name, xf, fn)`: real glTF node (kept by gltfpack with `-kn`), e.g. `wheel_FL`, `arm_L`.
  Animation clips: `b.clip(name, tracks)`.

## Writing a recipe

Create `tools/gen/assets/<area>.mjs` exporting `assets`:

```js
export const assets = [{
  id: "prop_bollard_a",     // file name, unique
  category: "prop",         // building | prop | sign | vehicle | character
  tags: ["sidewalk_small"], // how tools/gen/city.mjs finds it
  budget: 120,
  build(b, rng, params) {   // b = ModelBuilder, rng = seeded random
    b.lathe("mat_metal_painted_dark", [[0.12, 0], [0.12, 0.9], [0, 0.95]], { seg: 8 });
  },
}];
```

Builder API (`tools/gen/lib/builder.mjs`): `box`, `boxC`, `prism` (any footprint), `poly`, `wall`, `quad`,
`tri`, `cylinder`, `sphere`, `lathe`, `loft`, `tube`, `mesh`; transforms `with({pos, rotY, rot, scale}, fn)`,
`node(name, xf, fn)`, `place(asset, xf, rng, params)`; `anchor`, `collider`, `clip`; defaults `b.ao`, `b.tint`.
Winding rule for raw `tri`/`mesh`: `cross(b-a, c-a)` points along the outward normal.
Compass headings, metres, front = +Z.
